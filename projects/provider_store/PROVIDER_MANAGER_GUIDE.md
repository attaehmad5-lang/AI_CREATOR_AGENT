# Provider Manager Guide (Task #25)

This guide describes the current implementation in this branch. It is not a claim that the full A–P checklist is complete.

## Components

- `connection_manager.py` — provider catalog discovery, registration, enabled/disabled state, callable contracts for every modality present in the 54-provider catalog (including advanced editing, upscaling, transcription, audio, story, and video-editing categories), credential-presence checks, endpoint policy, and verified connection state. It accepts an injected `ProviderSecretsManager` for `secret_ref` presence checks; it never reads the secret during catalog inspection or persists secret values. Public catalog views rename legacy `status` to `catalog_status`; only a successful probe can set runtime connection state to `CONNECTED`. For API-key probes, `configure_provider(..., authentication_required=True)` must be used only for an endpoint documented to validate that credential; public model-list endpoints cannot prove authentication.
- `http_probe.py` — optional standard-library HTTPS probe for explicitly configured endpoints, with mandatory allowlist validation, TLS verification, no automatic redirects, bounded response reads, timeout propagation, provider-specific API credential headers, and safe HTTP status / `Retry-After` metadata. A configured `secret_ref` is resolved as a short-lived lease for the probe; request/header references are cleared after the call. Credentialed probes fail closed unless `authentication_required=True` is persisted for an endpoint documented to require and validate the supplied credential. A generic HTTP 2xx never proves generation capability or account credit balance.
- `log_safety.py` — namespaced application loggers, structured-value redaction, credential/token pattern scrubbing, exception/stack scrubbing, safe JSON formatting, and bounded recursive handling. Application modules should use `get_provider_logger(__name__)`; the full-source AST regression scan rejects raw secrets and traceback logging sinks.
- `oidc_identity.py` — cryptographically verifies signed OIDC JWTs with an exact issuer and API audience, an explicit algorithm allowlist, required `iss`/`aud`/`sub`/`iat`/`exp` claims, maximum token age, optional MFA claim enforcement, and a cached HTTPS JWKS resolver with a hostname allowlist, response limits, TLS verification, and redirects disabled. When configured on `ProviderService`, all service authorization gates reject caller-supplied principal IDs and require the exact opaque principal returned by `authenticate_bearer_token(authorization_header)`. API middleware must pass the Authorization header, keep the returned principal server-side, never accept principal IDs from request bodies, and never serialize/cast the principal. The deployment must configure its real issuer, audience, JWKS URI/host and MFA policy; this repository does not select or activate an identity provider by default.
- `encrypted_state_store.py` — optional AES-256-GCM authenticated encryption for JSON state files. A deployment-provided callback returns a 32-byte key for a stable per-store context; keys are never generated or stored by the repository. The encrypted envelope binds the purpose context as authenticated additional data, uses a fresh 96-bit nonce per write, enforces file/payload size limits, writes atomically with restrictive temporary-file permissions, and fails closed on wrong keys, tampering, malformed envelopes, or plaintext when encryption is enabled. Existing plaintext files are migrated only when `migrate_legacy_plaintext_state=True`, and the manager performs that migration under its interprocess lock. `ProviderAuthorizationManager`, `ProviderTenantIsolationManager`, and `ProviderJobManager` accept `state_encryption_key_provider` and context arguments; encryption is opt-in and requires the deployment to supply/manage keys securely. This does not automatically encrypt every other provider-store manager or replace database/disk encryption controls.
- `sensitive_data_policy.py` — bounded pre-routing inspection of nested provider-bound options, detecting credential-shaped values, secret-bearing field names, common API token/JWT/basic-auth/private-key/credentialed-URL patterns, email, phone, and Luhn-valid payment-card numbers. Reports only safe categories and structural paths, never matched values; supports configurable blocking, node/depth/text/finding limits, cycle detection, generic Mapping traversal, and fail-closed behavior on traversal errors. `ProviderService.execute_routed_request()` scans adapter options and routing options before provider selection, and `route_request()` independently scans direct callers' routing options before invoking the routing manager; both paths fail closed and do not invoke routing/adapters when the scan blocks or fails. Environment variable names and secret-reference metadata are excluded from value-field blocking. The configured policy also runs before service-managed provider configuration writes and access-control mutations (role assignment, provider-scope updates, and principal disablement), so blocked endpoints or identity data are rejected before manager persistence. This remains outbound/inbound service-boundary protection, not complete data-at-rest, retention, deletion, or deployment-wide privacy enforcement. The job-service read/write facade also removes worker-only `lease_token` values from submit/poll/complete/cancel responses (the claim response alone retains the token for the worker) and scans returned job records when the policy is configured, failing closed without returning the record when blocked sensitive data is found. Before a job is persisted, `ProviderService` also scans submission metadata (including payload references), worker identity on claim, and completion metadata (including result references); scan failures and blocked values stop the write. The active worker lease token itself is treated as a required transient verifier and is not scanned or persisted in plaintext; only its SHA-256 digest is stored.
- `secrets_manager.py` — `env://NAME` and injected backend resolution for references such as `vault://...` / `aws-sm://...`; short-lived `SecretLease` objects, tenant credential authorization, redacted backend failures, and confirmed, authorized, idempotency-keyed rotation hooks. Vault/cloud SDK adapters are supplied by the deployment; this repository does not enable a remote vault client or rotation operation automatically.
- `oauth_pkce_manager.py` — OAuth 2.0 authorization-code + PKCE (S256) for public clients, with allowlisted HTTPS authorization/token endpoints, one-time expiring state, bounded token responses, redirect rejection, in-memory-only tokens, and explicit refresh only when a refresh token exists. It does not implement client-secret OAuth or persist tokens across restarts.
  - `begin_pollinations_authorization()` uses Pollinations' documented `enter.pollinations.ai/authorize` and `/api/oauth/token` endpoints, requires a registered exact redirect URI, reads the publishable App Key from `POLLINATIONS_APP_KEY`, and requests `profile usage`. Pollinations does not issue refresh tokens, so its session requires re-authorization after expiry.
- `routing_manager.py` — priority, free-credit-first, lowest-cost, healthiest-first, and round-robin selection; requires a verified runtime connection by default (catalog labels alone are not evidence), with an explicit catalog-only planning option; optional health, cost, credit, and quota managers; duplicate request reservations fail closed; explicit fallback behavior.
- `credit_manager.py` — stores verified free-credit snapshots from an injected provider-specific probe, filters by compatible units, and atomically reserves/commits/releases local credit usage to prevent concurrent overspend.
- `account_balance_probe.py` — bounded HTTPS JSON balance probe that requires an explicit host allowlist, environment-only credentials, a documented auth-protected endpoint, and an explicitly confirmed response field representing available credits. It rejects ambiguous key-budget fields unless the caller has verified the field semantics; no response body or token is returned.
- `cost_policy.py` — paid-approval guard, required project budgets, idempotent usage reconciliation, estimated-cost reservations, and `finalize_usage()` which atomically validates charge outcomes and idempotency keys against the reloaded ledger before committing usage.
- `quota_manager.py` — hourly/daily/monthly UTC quota windows and request reserve/commit/release.
- `health_manager.py` — bounded provider health history, staleness/latency checks, eligibility, and a bounded persisted request-ID ledger so repeated finalization cannot append duplicate health events or silently reuse an ID for a conflicting result.
- `retry_policy.py` — bounded backoff decisions that consume validated HTTP status / `Retry-After` metadata from typed provider errors, plus a concurrency-safe circuit breaker with half-open probe-slot recovery when an attempt is cancelled.
- `output_validator.py` — bounded file reads, file-mutation detection during validation, file size/extension/signature/basic-content checks, JSON depth limits, and SHA-256 for supported artifacts.
- Provider-specific permissions: authorization records may carry `provider_scopes`, an operation-to-provider-ID allowlist. Once configured, every provider-scoped action missing from that map is denied; route generation filters candidates before choosing the primary/fallback provider. `ProviderService.configure_provider()`, `set_provider_enabled()`, and `set_provider_access_scopes()` enforce the matching admin permission. Legacy records without a `provider_scopes` field keep their pre-existing role-wide access until an administrator scopes them. Custom authorization adapters used for provider-scoped actions must explicitly declare `supports_provider_scopes = True` and accept the `provider_id` keyword; otherwise the service denies the action with `PROVIDER_SCOPE_ENFORCEMENT_UNAVAILABLE` rather than silently falling back to global role permissions.
- `provider_authorization.py` — versioned, atomic role assignments with viewer/creator/operator/billing-manager/admin permission sets. Administrative role assignment and principal disablement must go through `ProviderService.assign_provider_role()` / `disable_provider_principal()` and require `provider.access.manage` (admin only); underlying manager mutation methods are trusted in-process primitives, not public API endpoints. The final active administrator cannot be disabled or demoted. `principal_id` must come from trusted authentication middleware; this package does not itself validate identity-provider tokens, passwords, MFA, issuer, or audience.
- `provider_service.py` — integration facade for API/OAuth/manual connection verification, health recording, routing, output checks, retry decisions, and usage finalization. Managed-credential execution is opt-in (`use_managed_credential=True`) and only invokes adapters whose signature accepts `provider_credential_lease`; the service passes the lease object, not a raw token string. `verify_http_provider()` wires the built-in allowlisted HTTPS probe into connection-state and health recording; `verify_oauth_provider()` passes an OAuth manager's unexpired access token through an ephemeral environment mapping without persisting it. Configure `probe_endpoint` separately from `endpoint` to verify an auth-protected, non-billable account endpoint without replacing the generation endpoint.
- `provider_catalog.json` and `provider_catalog_master.json` — one synchronized 54-provider registry, including the 18 advanced-provider records. Catalog v3 requires complete provider identity fields and explicit `enabled` / `subscription_required` booleans; provider IDs and documentation/subscription links are validated before acceptance. The master catalog is the fallback copy, and the older v2 backup remains archival.
- Legacy store, category, advanced, unlock, status, and unified-registry/router facades now read the central catalog. Discovery facades distinguish catalog labels from live verified state; actual policy-aware execution still belongs to `ProviderRoutingManager`.

## Safety contracts

1. **No automatic purchases.** These modules do not purchase credits, start subscriptions, or infer paid approval.
2. **Paid usage requires both explicit provider approval and a configured project budget.** Paid project budgets and estimates are USD-denominated in this implementation; paid routing rejects other cost units. Reserve the estimate before execution. Zero-cost routes are allowed only when the provider catalog explicitly sets `zero_cost_allowed: true`; a zero estimate alone is not proof that a provider is free. After an actual provider request starts, reconcile the actual cost and commit its quota even if the generation failed.
3. **Free credits must be evidence-based and unit-compatible.** Configure `ProviderCreditManager` with an injected, provider-specific account-balance probe. The probe must return a verified balance, source, and unit; it may include the provider's observation time, otherwise the manager records the local observation time when the probe returns. The probe must query a trusted provider account source rather than reuse an old cached balance. Routing must not compare unlike units (for example, provider credits against a USD estimate). Free-credit routes require an idempotency/request ID and reserve credits before routing; after the provider request starts, commit the reservation unless the provider confirms credits were not consumed. Release only when the request is known not to have started or could not consume credits. Refresh is blocked while reservations are in flight and cannot erase local usage with a snapshot observed at or before the latest local debit, and snapshot timestamps cannot regress. Direct `ProviderCostPolicy` calls and caller-supplied numeric maps cannot authorize free usage; only the routing path with its injected credit manager may do so. No generic injected probe is proof of a live provider account balance.
4. **Do not release reservations just because a provider failed.** A failed API request may still consume quota or cost. `select_fallback` keeps reservations by default and requires a new attempt ID when a previous attempt may have started. Set `release_reservations=True` only when the caller knows the provider request did not start or could not be billed.
5. **Connectivity checks are injected.** `ConnectionManager.verify_connectivity` passes a timeout to the probe, but arbitrary Python callbacks cannot be forcibly stopped if they ignore it. Each provider-specific probe must enforce its own network timeout. Credentialed generic HTTP probes require `authentication_required=True` only when official provider documentation confirms that endpoint validates the credential. Account-based providers must use `verify_manual_connection` with a live, user-authorized session; the session object is never persisted, and the injected probe must actually validate it. OAuth PKCE tokens and pending verifiers stay in memory only; token refresh is explicit, and providers that issue no refresh token require a new authorization flow. Routing requires a persisted `CONNECTED` state with `verified=true` by default; `require_verified_connection=False` is intended only for explicit catalog/planning workflows, not real execution.
6. **Output validation is not full decoding.** Signatures and basic content checks detect many mismatches, but do not replace media decoding, malware scanning, or semantic quality checks.
7. **Persistence limits.** Shared JSON state for provider connection/catalog, health, credits, cost budgets, and quotas uses atomic replacement plus OS-level interprocess lock files and reload-before-mutate. `ProviderJobManager` applies the same locked atomic persistence pattern and stores worker lease-token SHA-256 digests rather than raw token values; legacy plaintext lease records are migrated under the state-file lock without invalidating an already-issued worker token. This prevents lost read-modify-write updates across local processes when every writer uses these manager APIs. It is not a single transaction across multiple manager files, and it does not coordinate separate devices, containers with non-shared lock semantics, or external writers bypassing these APIs. Routing compensates reservations created by the current attempt when a later quota step rejects the route, and fails closed if that compensation fails; this reduces orphaned reservations but does not make the separate JSON files one atomic transaction. SQLite or a transactional database is preferred for production multi-worker coordination.
8. **Secrets stay outside the catalog.** Store environment-variable names or references, not credential values. Returned provider metadata and state views redact credential-like fields. `ProviderSecretsManager` validates references and authorizes tenant ownership before retrieval when tenant isolation is enabled. It returns a short-lived lease; the service passes that lease only to an explicitly compatible adapter and closes it after invocation. Rotation requires `provider.credentials.rotate`, explicit confirmation, an idempotency key, and a backend implementing `rotate_secret`. External backends must enforce workload identity, request timeouts, audit logging and idempotency. Closing clears the lease's internal byte buffer, but cannot guarantee erasure of immutable string copies created by a trusted adapter.

## Explicit catalog recovery

`ConnectionManager.restore_catalog_from_master()` restores the provider catalog only when the target is missing or fails validation. It validates the master copy first, refuses to overwrite an already-valid target, uses the target's interprocess lock, and reports a safe status instead of silently replacing a valid catalog.

Numeric request values are normalized with overflow-safe finite-number checks before they reach cost, credit, routing, connection, health, retry, OAuth, and account-balance policies.

Run from the repository root:

```python
from projects.provider_store.connection_manager import ConnectionManager

result = ConnectionManager.restore_catalog_from_master()
print(result)
```

This restores catalog metadata only; it does not restore credentials, connection sessions, quota ledgers, or credit/cost history.


For a local Hugging Face credential check, set `HF_TOKEN` in the process environment (never paste it into source code or print it), then run this from the repository root. It checks the documented authenticated identity endpoint, not generation credits or model availability:

```python
import os
from projects.provider_store.connection_manager import ConnectionManager
from projects.provider_store.provider_service import ProviderService

manager = ConnectionManager()
configured = manager.configure_provider(
    "huggingface",
    probe_endpoint="https://huggingface.co/api/whoami-v2",
    authentication_required=True,
)
if configured.get("saved") is not True:
    print(configured.get("status", "CONFIGURATION_FAILED"))
else:
    result = ProviderService(manager).verify_http_provider(
        "huggingface", environ=os.environ
    )
    print({
        "status": result.get("status"),
        "verified": result.get("verified"),
        "health": (result.get("health") or {}).get("status"),
    })
```

This probe does not display the account response body or token. Do not run it in CI with a personal token; execute it only in the user's local authorized environment.

Live provider API/account probes, provider-specific OAuth registration/token-refresh integrations, complete multimodal adapters, full media decoding and semantic validation, end-to-end generation execution, provider-specific network-failure injection, cross-manager atomic transactions, and individual evidence-based verification of every item in the canonical feature checklist remain separate requirements. Fine-grained capability discovery uses only explicitly declared capability strings; a category label does not prove every advanced capability.

## Feature 69 — Sensitive-data boundaries and encrypted persistence

`ProviderService` creates a `SensitiveDataPolicy` by default when a deployment does not inject a custom policy. The bounded scanner returns categories and structural paths only; it never returns matched values. Credentials are blocked by default. Email, phone and Luhn-valid payment-card values are detected and reported; deployments may add those categories to `blocked_categories` when their content-handling rules require it. Scan errors, invalid scanner responses, cycles and traversal-limit exhaustion fail closed.

The service checks caller-controlled routing/adapter options before routing, and scans routing-manager, webhook-verifier, adapter and downstream manager result values before exposing those results. If an adapter response is blocked after the provider may already have started work, the service marks the outcome unknown and retains reservations; it must not infer that a potentially billable call was free. Job submission/claim/completion metadata is checked before persistence, and public job responses remove worker-only lease verifiers.

`EncryptedJSONStateStore` can also encrypt these persistent manager state files when a deployment supplies a KMS/secret-manager-backed key callback:

- `ProviderAuthorizationManager` — `provider-authorization-v1`
- `ProviderTenantIsolationManager` — `provider-tenant-isolation-v1`
- `ProviderJobManager` — `provider-job-state-v1`
- `ProviderCostPolicy` — `provider-cost-ledger-v1`
- `ProviderQuotaManager` — `provider-quota-state-v1`
- `ProviderCreditManager` — `provider-credit-state-v1`
- `BudgetAlertManager` — `provider-budget-alerts-v1`
- `ProviderWebhookVerifier` — `provider-webhook-replay-v1`
- `ProviderIncidentManager` — `provider-incident-state-v1`

Each manager accepts `state_encryption_key_provider`, plus an optional `state_encryption_context` override. The callback must return the 32-byte key for the supplied context from deployment-managed key storage. Never hard-code keys, store them beside state files, or commit them. To migrate an existing plaintext state file, set `migrate_legacy_plaintext_state=True` for the controlled migration startup; the read and rewrite occur under the manager's interprocess lock. The manager rejects plaintext by default once encryption is enabled. After successful migration, disable the migration flag for normal operation.

**Deployment limitation:** encryption remains opt-in to preserve existing deployments that have not provisioned a key service. Files for other provider-store components, the provider catalog/configuration, external databases, backups and generated user assets are not automatically encrypted by this feature. The deployment must explicitly configure each supported manager, protect backups/disks, provide key recovery/rotation, and test restoration. This work does not yet implement a deployment-wide retention schedule or a verified deletion workflow across provider-side copies; do not represent those controls as complete.
